daplis_rtp.gui.theme module

Where every colour, font size and plot style in the application comes from.

One object holds the lot - the window palette, the accent, the colours the traces are drawn in, the two font sizes - and one signal says it has changed. Nothing else in the package hard-codes a colour.

The reason is that the old application chose its colours in a dozen places: plt.style.use("dark_background") in three canvas modules, #f48383 and teal written into the plotting calls, qdarkstyle on the application, and a setPointSize on very nearly every widget built. Changing the look meant finding all of them, and a user who wanted a lighter background, or a colour they could actually distinguish, had nowhere to say so.

Two rules keep it that way:

  • Widgets do not set their own font. The application font is set here and inherited; a widget that needs a different one gets an object name and a rule in the stylesheet below. A per-widget setFont pins that widget at the size it was built with and ignores every later change.

  • Canvases ask for their colours when they draw. They hold no copies, so a theme change is a redraw, not a rebuild.

Settings are stored per user through QSettings - on Windows in the registry under HKCU\Software\DAPLIS\daplis-rtp - so two people sharing a machine keep their own.

Frozen because a theme is a value, not a thing that is edited. The user’s changes are kept separately, as overrides, and applied with dataclasses.replace when the effective theme is built - so “reset to preset” is throwing the overrides away rather than reconstructing anything.

class daplis_rtp.gui.theme.ThemeManager(parent=None)[source]

Bases: QObject

The live theme, the user’s changes to it, and who to tell.

One of these exists per process - see theme_manager(). It is a QObject for one reason: it emits a signal. Everything that draws connects to changed and redraws itself, which is what makes a colour picked in the Preferences dialog show up on the plot while the dialog is still open.

Put the current theme on the application.

The font goes on the QApplication rather than on the widgets, so that every widget built before or after this call picks it up. That is the whole reason nothing in the package calls setFont any more.

load()[source]

Read the stored settings, ignoring anything unrecognised.

A stored value that no longer names a field - a preset that was renamed, a colour written by a newer version - is skipped rather than raising. A settings file is not something the user can easily repair, so it must never be able to stop the application opening.

mpl_rc(fontsize=None)[source]

The theme as matplotlib rcParams.

Handed to rc_context around a draw rather than pushed into the global rcParams. The old code called plt.style.use at import time and plt.rcParams.update from inside draws, which meant the last canvas to be built decided how all of them looked.

stylesheet()[source]

qdarkstyle for the controls, our own rules on top.

qdarkstyle is kept because it styles the sixty-odd widget classes Qt ships and nobody wants to write that. What it does not know about is this application’s accent colour and the handful of named widgets - the tab title, the hint line, the log - that need to look different from their neighbours.
